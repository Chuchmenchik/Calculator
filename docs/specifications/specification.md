# 📜 Architectural Specification: Blox Fruits Remote Project

## 1. Обзор проекта
**Цель:** Создание модульного чита для Blox Fruits (Roblox) с динамической подгрузкой компонентов.
**Платформа:** Roblox (Executor: Xeno).
**Язык:** Lua.
**Метод доставки:** Remote Loader (загрузка скриптов через `raw.githubusercontent.com`).
**Ключевая особенность:** Высокая модульность для работы AI-агентов с ограниченным контекстным окном.

---

## 2. Архитектурные принципы
1.  **Принцип изоляции:** Каждый модуль должен быть максимально независимым. Сбой в одном модуле не должен приводить к краху всего проекта.
2.  **Единый источник истины (SSOT):** Все конфигурации и список активных модулей хранятся в `manifest.lua`.
3.  **Слой абстракции:** Прямые обращения к игровым объектам и RemoteEvents разрешены только в `GameAPI.lua`.
4.  **Событийная модель:** Взаимодействие между модулями (особенно между Логикой и UI) происходит через `EventBus`.
5.  **Стандартизация API:** Все функциональные модули должны иметь идентичный интерфейс управления.

## 4. Технические спецификации компонентов

### 4.1. Remote Loader (`loader.lua`)
Загрузчик является единственным файлом, который пользователь вставляет в эксплойт.
**Алгоритм работы:**
1. Загружает `manifest.lua`.
2. Итерирует список модулей в порядке, указанном в манифесте.
3. Для каждого модуля:
   - Загружает код через `loadstring(game:HttpGet(url))`.
   - Оборачивает выполнение в `pcall`.
   - Если модуль успешно загружен, вызывает его метод `.Init()`.
4. В случае ошибки модуля — выводит уведомление в консоль/UI и переходит к следующему.

### 4.2. Манифест (`manifest.lua`)
Файл в формате Lua-таблицы, определяющий состав проекта.
**Структура:**
```lua
return {
    Modules = {
        { name = "State", path = "core/State.lua", priority = 1, enabled = true },
        { name = "EventBus", path = "core/EventBus.lua", priority = 2, enabled = true },
        { name = "GameAPI", path = "api/GameAPI.lua", priority = 3, enabled = true },
        { name = "AntiCheat", path = "system/AntiCheat.lua", priority = 4, enabled = true },
        { name = "Interface", path = "ui/Interface.lua", priority = 5, enabled = true },
        { name = "AutoFarm", path = "features/AutoFarm.lua", priority = 6, enabled = true },
    }
}
```

### 4.3. Глобальное состояние и EventBus
- **State:** Использует `getgenv().BF_Cheat = {}` для хранения настроек, текущего статуса и общих переменных.
- **EventBus:** Реализует методы `Subscribe(eventName, callback)` и `Fire(eventName, ...)`. Позволяет модулям общаться, не имея прямых ссылок друг на друга.

### 4.4. GameAPI (Слой абстракции)
Все взаимодействия с игрой (например, `game:GetService("ReplicatedStorage").Remotes.Attack:FireServer()`) выносятся сюда.
**Пример:**
- Вместо прямого вызова RemoteEvent в `AutoFarm.lua`, используется `GameAPI.Attack()`.

### 4.5. Стандарт модуля (Feature Module API)
Каждый файл в папке `features/` должен возвращать таблицу следующего вида:
```lua
local Module = {}

function Module.Init() 
    -- Настройка переменных, подписка на события EventBus
end

function Module.Start() 
    -- Запуск основного цикла/логики
end

function Module.Stop() 
    -- Остановка циклов, очистка ресурсов
end

return Module
```

### 4.6. Пользовательский интерфейс (UI)
- Используется внешняя библиотека (Rayfield/Orion).
- **Логика:** UI не содержит бизнес-логики. Он вызывает `Module.Start()` или `Module.Stop()` и подписывается на `EventBus` для обновления текстовых полей/индикаторов.

## 5. Правила разработки и расширения

### Добавление новой функции (Feature):
1. Создать новый файл в `features/`.
2. Реализовать методы `Init`, `Start`, `Stop`.
3. Добавить запись о модуле в `manifest.lua` с соответствующим приоритетом (после UI и GameAPI).
4. В `Interface.lua` добавить кнопку/переключатель, связанный с этим модулем.

### Изменение игровой логики:
1. Если изменился RemoteEvent или путь к объекту в игре $\rightarrow$ изменить только в `GameAPI.lua`.
2. Если изменилась логика работы функции $\rightarrow$ изменить только в соответствующем модуле `features/`.

---

## 6. Pipeline: Сборка и Деплой
1. **Разработка:** Локальное написание кода $\rightarrow$ Тестирование в Xeno.
2. **Деплой:** Push в GitHub репозиторий.
3. **Обновление:** Поскольку загрузчик всегда тянет актуальные файлы с `raw.githubusercontent.com`, обновление происходит мгновенно для всех пользователей при перезапуске скрипта.
4. **Будущее:** Внедрение обфускатора в CI/CD пайплайн перед пушем в `main` ветку.

---

## 7. Инструкция для AI-агента
При работе над проектом агент должен:
1. **Сначала изучить `manifest.lua`**, чтобы понять текущий состав проекта.
2. **Запрашивать `GameAPI.lua`**, прежде чем писать любой код, взаимодействующий с игрой.
3. **Соблюдать структуру API модуля** (`Init`, `Start`, `Stop`).
4. **Использовать `EventBus`** для синхронизации между модулями.
5. **Не вносить изменения в `loader.lua`** без крайней необходимости, так как это точка входа.
6. **Предлагать обновления спецификации**, если в процессе разработки внедряется новый архитектурный паттерн.
